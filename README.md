# Mobox-WCS 业务流程说明

## 一、 系统概述与边界
本流程描述了 WMS（仓储管理系统）与 WCS（仓储控制系统）之间的交互机制。
WCS 采用“脚本驱动”和“后台线程异步轮询”的设计，负责将上层任务转化为底层设备动作，并接收设备反馈。

## 二、 核心流程阶段

### 阶段 1：任务下发与作业创建
1. WMS 调用 WCS 提供的接口，下发任务请求。
2. WCS 接收请求后，在系统中创建一条“作业（Job）”记录。

### 阶段 2：作业启动与任务生成
1. WCS 后台线程轮询读取处于“等待状态”的作业。
2. 通过作业名称，匹配对应的“作业启动脚本”。
3. 执行该启动脚本，完成作业启动。
4. 作业启动成功后，系统创建具体的“任务（Task）”记录。

### 阶段 3：任务推送前置校验
1. WCS 后台线程读取刚创建的任务，检查当前任务类型。
2. 检查是否存在该类型对应的“推送校验脚本”：
   - 若存在：执行该脚本，根据脚本业务逻辑返回“可推送”或“不可推送”。
   - 若不存在：系统采用默认放行策略，默认返回“可推送”。
3. 根据上述逻辑，最终判定该任务是否允许推送。

### 阶段 4：任务推送
1. WCS 后台线程轮询读取处于“等待推送”状态的任务。
2. 执行对应任务类型的“任务推送脚本”。
3. 将任务推送至底层可编程接口（设备接口）。

### 阶段 5：动作监听与任务完成
1. 可编程接口接收来自设备的信号。
2. WCS 创建设备动作队列。
3. WCS 后台线程触发对应的“监听脚本”。
4. 执行动作监听逻辑。
5. 任务完成后，执行后续处理逻辑。

## 三、 关键机制与设计意图（供 AI 分析代码时参考）

1. **脚本驱动（Script-Driven）**：流程高度依赖“作业名称”和“任务类型”去匹配外部脚本（如 Lua）。这是一种可插拔的业务扩展设计。代码审查时，需关注脚本匹配逻辑的健壮性（如匹配不到脚本时的降级处理）。
2. **默认放行策略（Default Allow）**：在“推送前校验”环节，如果找不到对应的校验脚本，系统默认返回“可推送”。这表明系统设计倾向于可用性优先，业务拦截属于可选配置。审查代码时需注意此处的业务安全隐患。
3. **异步解耦（Asynchronous Decoupling）**：通过“后台线程”轮询处理作业和任务的各个状态（等待作业、等待推送任务），说明 WCS 与上层系统、底层设备之间是异步通信的，以避免接口阻塞。审查代码时需关注后台线程的异常捕获、死循环风险以及并发读写问题。
4. **状态机流转**：作业和任务均存在明确的状态（如等待、启动、等待推送、完成等）。审查代码时需重点关注状态流转条件是否严格。
